# アーキテクチャ

## 現在の構成

現在は`Eluna.App`という一つのWPFプロジェクトです。ViewModelsに会話状態、Servicesにモデル取得・保存・推論エンジンの管理、Modelsにデータを配置しています。WPFがllama.cppサーバーを管理し、ループバックHTTP / SSEで応答を受け取ります。外部C#ライブラリはありません。

## 推論との接続方針

アプリが管理する`llama-server.exe`とループバックHTTPで通信します。`System.Diagnostics.Process`、`HttpClient`、`System.Text.Json`を使い、外部C#バインディングやAPI SDKを追加しません。APIキーはセッションごとに生成し、Windows Job Objectでアプリ終了時の子プロセス終了も保証します。

ネイティブコードを別プロセスにすることで、モデルの読み込み失敗や推論側の終了からUIを回復できるようにします。サーバーのAPI仕様は固定コミットの[公式ドキュメント](https://github.com/ggml-org/llama.cpp/blob/6868a52cb337450658006ad2f9281c2eb63f1666/tools/server/README.md)を基準にします。

実装時には次の責務を分けます。

| 責務 | 配置・方針 |
| --- | --- |
| 表示・入力 | Eluna.AppのView / ViewModel。コードビハインドは画面固有処理に限定 |
| 会話・生成状態 | UIに依存しないモデルとサービス。必要になった時点でEluna.Coreに分離 |
| サーバー管理・通信 | 起動、準備完了、HTTP / SSE、キャンセル、終了を扱うEluna.Inferenceに分離 |
| 履歴・設定 | .NET標準のJSON / ファイルAPI。必要になった時点で保存サービスを追加 |

まだ必要でないプロジェクトや抽象基盤を先に作りません。DIコンテナ、MVVMフレームワーク、ORMは導入せず、通常のコンストラクターと標準インターフェースを使います。

## 実装時の条件

- UIスレッドでモデル読み込みや推論・保存を待たない。
- サーバーは`127.0.0.1`に限定し、ポート競合と準備完了タイムアウトを扱う。ループバックだけで認証は完結しないため、アプリ管理サーバーにはセッションごとのAPIキーも検討する。
- モデル切り替え、キャンセル、アプリ終了では、アプリが起動した子プロセスだけを後始末する。
- 会話の保存先は`%LOCALAPPDATA%/Eluna/`を基本とし、インストール先への書き込みを前提にしない。
- 保存は一時ファイルと置き換えを使い、形式のバージョン、破損時の回復、移行を設計する。
- プロンプトや会話本文を通常のログに出さない。ネットワーク通信やテレメトリーは利用者に分かる形で設計する。

初期GPUバックエンドはVulkanです。開発用の共有ライブラリ構成と、配布用の一体構成を分けています。配布用exeにはCPU / Vulkanそれぞれの静的CRTエンジンを埋め込み、起動時にユーザーフォルダーへ展開します。モデルのレイヤー配置は標準では`auto`を指定し、VRAM容量に応じた調整をllama.cppに任せます。GUIの設定でGPU / CPUを指定できます。自動モードでGPU読み込みが失敗した場合はCPUへの再試行を画面へ表示します。

対応するWindowsバージョンの下限、ARM64、インストーラー、Markdownの表示範囲は今後の実機確認を踏まえて決めます。CUDA / HIP / SYCLなどの追加SDKは今回の承認に含めません。

応答モードはリクエストごとに指定し、モデルやエンジンの再起動を伴いません。固定コミットの`/v1/chat/completions/input_tokens`で会話の入力長を数え、思考枠と出力上限を調整します。SSEの`reasoning_content`と`content`を分け、ViewModelへ状態として渡します。思考本文は保存せず、思考時間と選択モードを任意フィールドとして既存の履歴形式へ追加しています。

プロジェクト・ナレッジはJSONの任意フィールドとして追加し、旧形式の会話は所属なしで読み込みます。初回のナレッジ保存時に形式2の`state-knowledge.json`へ移し、旧版が使う`state.json`は変更しません。`KnowledgeService`が会話の所属IDで候補を先に限定し、共通情報の利用可否を判定してから、メモリ・資料・同じプロジェクトの現在の会話分岐を検索します。不明な所属IDは通常チャットへフォールバックせず拒否します。資料やメモリの参照には全プロジェクト横断のキャッシュを使いません。選んだ抜粋は利用者指示とは別の参考資料としてモデルへ渡し、通常チャット・調査の入力token数にも含めます。回答には生成時の抜粋を保持し、後から資料が編集されても当時の入力を確認できます。[仕様と制約](knowledge.md)を参照してください。

## 会話ごとの推論予約

`InferenceQueue`は予約と同時実行数、会話単位の順序を管理する。`ChatViewModel.Queue`がモデル・設定・ナレッジの予約時スナップショットと分岐／回答IDを保存し、独立した`LlamaService`を各実行枠へ割り当てる。UIの選択状態を処理の参照先として使わない。会話履歴は実行開始時に該当回答より前だけを取り出す。状態ファイルに依頼とメッセージを一緒に保存してから開始し、再起動では再開待ちにする。詳細は[並行作業ガイド](concurrent-work.md)。

## スキル

`SkillStore`はSKILL.md・ZIPの取り込みと不変の版、同梱ファイルの検証を扱う。`SkillRunner`はスコープを限定したメタデータから適用を選び、本文・参考資料・補助コードを段階的に読み込む。`SkillScriptRunner`はWindows標準PowerShellの確認・専用作業フォルダー・出力制限・キャンセルを扱う。OSによるコード隔離ではない。

予約には候補のメタデータと版IDを保持し、実行時の画面選択に依存させない。使用した本文・抜粋・実行結果は回答へ保存する。プロジェクト外のスキルは初期状態で候補から除外する。形式3の`state-skills.json`は登録情報・会話ごとの選択・使用記録を保存し、従来の状態ファイルを残す。版の実ファイルと生成ファイルは別管理。詳細は[スキルガイド](skills.md)。

## Computer Use

`ComputerUseWindow`が対象選択・画面・提案の確認と文字修正・停止・履歴を扱い、`ComputerUseRunner`が観察→提案→確認→実行の回数・時間・許可範囲を管理する。`ComputerPlanner`は独立した`LlamaService`へ対象画面とUI要素を渡し、JSON schemaで単一操作を生成する。`ComputerActionPolicy`は形式・キー・パスワード欄・実行前の観察の一致を検査する。

`ComputerDesktop`は同じexeの`--computer-worker`を要求ごとに起動し、標準入出力のJSONで通信する。補助プロセスのMTAスレッドがUI Automation / Win32 / GDIを扱い、12秒の要求期限とWindows Job Objectで終了させる。UIAプロバイダーが応答を止めてもWPFを止めない。前面化の前後で観察を比較し、入力先のフォーカス・マウス位置を検査する。OSの入力制約を回避しない。

デスクトップの同時制御を名前付きmutexで1件に限定し、実行中だけCtrl+Alt+Escを登録する。`ComputerActivity`を処理リストへ表示する。終了・画面を閉じる・キャンセルで推論と補助プロセスを後始末する。画面・依頼・操作履歴は通常の保存状態へ加えず、利用者が選んだ履歴JSONだけを書き出す。詳細は[Computer Use](computer-use.md)。
