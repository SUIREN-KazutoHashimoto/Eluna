# 会話の並行作業と推論予約

## 使い方

- 推論中も履歴・プロジェクト・分岐を切り替え、新しいチャットや下書きを作れる。出力・停止操作は対象の会話に対応する。
- 送信すると推論を予約する。空きがあれば開始し、なければ順番を待つ。同じ会話の依頼は分岐が違っても順番に実行する。予約の上限は100件。
- サイドバーの「処理リスト」で推論・ダウンロード・作成処理の進捗と予約順を見る。実行中を先頭に表示し、会話を開く、個別停止・キャンセル、再開・再試行を操作する。「推論の履歴」から詳細一覧も開ける。完了・キャンセル済みの推論表示履歴は最大50件で、通常の会話本文は残る。
- 設定 → 一般 →「同時に実行する推論の数」で1〜4を選ぶ。初期値は1。増やすと待っている別会話を開始し、減らした場合は実行中の処理が終わるまで新しい開始を待つ。処理中の依頼を設定変更で中断しない。
- モデルを探す画面・取得管理は開いたまま主画面を操作できる。設定でダウンロードの同時取得数も1〜4件へ変更でき、完了したモデルは次の依頼から選べる。画像モデルの取得も共通のキューを使う。

## 予約が保持するもの

予約時のモデル・推論設定・思考量・検索モード・調査上限・ディベート参加者と、それぞれのモデル情報を保存する。プロジェクトの指示・メモリ・資料・他の会話から抽出したナレッジも予約時の抜粋で固定する。表示中のモデルやプロジェクトを変更しても予約へ反映しない。

対象会話の履歴は、その依頼より前のメッセージを実行開始時に読む。同じ会話の先行する回答を引き継ぎ、後から予約した質問・回答は混ぜない。分岐ID・回答IDで書き込み先を固定し、表示中の分岐に依存しない。履歴の要約も対象分岐に保存する。

実行中・予約中・再開待ち・失敗の依頼がある会話は、移動・削除・編集再生成を保護する。先に該当依頼を停止／キャンセルする。モデルの削除・保存先変更やバックアップ復元も、予約が残っていれば開始しない。予約後の資料変更は新しい依頼から反映する。

## 保存と終了

依頼と対象メッセージを同じ状態ファイルへ保存してから実行する。通常の終了では推論をキャンセルしてエンジンを終了し、未完了の依頼と途中の回答を保存する。再起動ではすべて再開待ちにし、検索や推論を勝手に再実行しない。異常終了では最後に保存した状態まで復元する。

再開ボタンを押すとチャットは保存した質問を再実行し、途中の回答を置き換える。調査・ディベートの既存チェックポイントがある場合はその進捗から再開する。失敗・再開待ちの依頼は、同じ会話の後続より先に再開またはキャンセルする。別の会話は続行する。

予約情報は`state-knowledge.json`内の`InferenceJobs`に格納する。スキルを利用して形式3へ移行した場合は`state-skills.json`に格納する。予約で共通指示・メモリを保持するため、このファイルも会話と同じ私的なデータとして扱う。バックアップ・全履歴エクスポートに含める。履歴の取り込みでは自動実行を避けるため予約を取り込まない。バックアップ復元では再開待ちとして復元する。旧版への再起動による書き戻しを防ぐため、予約を使い始めると従来の`state.json`から分かれた保存先を維持する。

## 実装と範囲

`InferenceQueue`がディスパッチャー上で予約・同時実行数・会話単位の順序を管理し、各実行枠は独立した`LlamaService`とllama-serverプロセスを使う。同じモデルでも重み・KVキャッシュの共有は行わない。空いたエンジンは次の依頼で再利用し、停止・縮小・終了時に解放する。増やすほどRAM・GPUメモリを使い、速度が必ず上がるわけではない。表示RAMはアプリと各エンジンのワーキングセットの概算合計。

Web検索・深掘り調査・ディベートも会話ごとの1ジョブとして数える。調査の計画確認は主画面を止めない別ウィンドウで行い、回答を待つ間もその実行枠を使う。ディベート参加者の工程はジョブ内で順番に実行する。

チャット・調査と、画像・文書の生成枠は独立している。設定でそれぞれ1〜4件に変更できる。画像・文書は最大20件の未完了／再開待ちの依頼を保持し、依頼ごとにエンジンと出力を分ける。画面を閉じても登録した生成は続行し、同じ画面から次の依頼を登録できる。文書生成のモデル・設定・指示・資料の抜粋・スキル版は操作時に固定する。

画像・文書の予約は`media-jobs.json`へ保存する。終了時に生成を止め、途中の本文と依頼を保持する。再起動時は再開待ちで復元し、処理リストから保存した依頼を最初から再実行できる。自動実行はしない。出力は「開く」から確認できる。履歴JSONの書き出し・世代バックアップはこの別ファイルを含まない。

補助ファイルの設定・資料OCR・モデル管理は個別操作の制約を保つ。準備操作は既存の推論が終了するのを待って排他で行う。モデル保存先変更中など、予約したファイルが不確定になる操作中は新しい送信を止める。ダウンロードは独立した並列キューで動き、一件だけの停止・失敗は他の取得を止めない。初期の同時取得数は1、ローカル取り込みは逐次実行。詳細・検証は[残機能の実装記録](remaining-features.md)を参照。

新しい外部パッケージやネイティブエンジンの変更はない。

## 検証

- `scripts/Verify.ps1`: 会話ごとの順序、別会話の追い越し、同時実行数の増減、個別キャンセル、失敗した先行依頼、終了、予約スナップショットの保存と不正な参照の拒否。
- 実モデル・WPF操作・描画: `Eluna.exe --data-dir <検証専用ディレクトリ> --verify-concurrent <model.json>`。4Bモデル2件の同時ストリーミング、プロジェクト参照の分離、表示モデル変更、下書き保持、個別停止、予約再開、明暗テーマと最小サイズを検証する。ダウンロード併走は、制御したHTTPストリームから実際の取得・書き込み・進捗・停止処理へ16KBを流して検証し、外部サイトからモデルを再取得する試験とは区別する。
